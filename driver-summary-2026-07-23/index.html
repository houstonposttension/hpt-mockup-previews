Driver summary — 4 frames

Ready-load detail (home) · still-loading detail · not-started detail · trip-ready hand-off. One phone screen per load, swipeable tabs across a multi-bin trip.
Frame 1Ready (home): "X8 · 22 of 22 · ready to depart" + customer / site / ship. Green gate; hand off to OptimoRoute.
Frame 2Still loading: "15 of 22" + what's not on the truck by where it is + "last tag 2 min ago". No fake ETA.
Frame 3Not started: nothing on the truck yet — waiting on the loader.
Frame 4Trip ready: whole-trip summary + a read-only acknowledgment that writes nothing.

Scope & open items

Hard boundary. Drivers already use the OptimoRoute driver app for route, turn-by-turn navigation and proof-of-delivery. This surface answers "is it ready?" and hands off to OptimoRoute the instant the wheels roll. Our system owns up to ON_TRUCK; DELIVERED is OptimoRoute's — the same loader/driver seam already written into the loader spec.

Open — O1 (assignment timing). OptimoRoute exposes which driver an order is assigned to only after the route is optimized (via search_orders · includeScheduleInformation). For a pre-departure "my loads" query to be non-empty, HPT must either pin loads via assignedTo up front or optimize the route before drivers reach the yard. If neither, v1 ships as driver self-select over /api/loadlist.json — the same tab strip, different source.

Open — Q10 confirmed. Home screen = per-load detail (not a list), swipeable tabs for multi-bin trips, first bin is home. Locked with James 2026-07-24.

Display-only gaps (documented, not built): G1 — the "last tag scanned" freshness line needs the LOADED event timestamp surfaced into /api/load-status. G2 — the loader's name is deliberately not shown (worker names are tenant-only, GA-WIP-015). No synthetic ETA is ever rendered.
