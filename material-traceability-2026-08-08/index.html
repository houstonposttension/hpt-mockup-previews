The rule table

Locked by James, 2026-08-08. The captured identifier is what is physically printed on the material and what the worker is asked for. It is not the same question as CertProcessor's cert-completeness rule, and for four rows the two genuinely differ — flagged ⚠ below and recorded in spec §2.3. Item type still uses CertProcessor's MaterialType vocabulary, because that is the join key to the cert data.

Five identifier types are in play: Heat, Serial, Lot, Batch, Date Code. The Cert Identifier Index models only the first three — adding Batch and Date Code is a cross-project change request with 9 sites, 3 of them structural (spec §6.5.1).

Three corrections the code forced on the brief 1 — it is not “a heat number”, and there are five types, not three. James's mapping (2026-08-08): Wedge and Anchor → Date Code; Resin and Colorant → Lot; Grease → Batch; Coil → Serial; Rebar → Serial or Heat. Only two of the seven in-scope types involve a heat at all, and both reach it indirectly, through a serial. Batch is a distinct type, not an alias for Lot.
2 — a WIP tag has no PO. The tags upsert (tagstore.py:1084-1088) writes order_num, an HPT Cloud sales order. CertProcessor's PO + HeatNumber filter cannot be reused as-is, so lookups scope by IdentifierType + MaterialType only — which per the Cert Identifier Index contract returns a set, not a row.
3 — the gate must not call CertProcessor inline. Both existing systems verify asynchronously: CertProcessor's own gate is a batch sweep that resets rows after the fact (enforce_completeness_gate.py), and Extrusion stores cert keys reconcile_status DEFAULT 'pending'. Binding a floor hard-stop to a Graph round trip makes SharePoint's availability the floor's availability. Capture is hard and local; verification is asynchronous.
The two questions this set was built to answer Extrusion — already covered? Half. The data model covers it thoroughly and predates this work by roughly seven weeks (extrusion.run_cert_link, cert-key types heat/serial/lot/batch, reconcile status, M:N — sql/001_extrusion_schema.sql:166-180). The operator mockup (5 operator frames) captures no identifier at all — lots live in a free-text Start-notes box. And Extrusion is a different app: config.py:64-68 removed it from SCAN_STATIONS because “emitting here would create orphan events”. So: rule stated here, implementation filed to Extrusion Log.

Identifier types — how many? Five. James supplied the real mapping 2026-08-08: Heat, Serial, Lot, Batch, Date Code. Batch is distinct from Lot, and Date Code was never modelled at all. The Cert Identifier Index knows three (identifier_parser.py:26), so every wedge, anchor and grease capture is unverifiable until CertProcessor widens it — a 9-site change, 3 sites structural, plus a live SharePoint choice-column edit. Worse, the source column Batch_x002f_Lot_x002f_Date_x002f conflates the three types the mapping separates, so the parser cannot mechanically emit the right one. Spec §6.5.1, Q9a/Q9b.

PT — whose design? Not this one's. uncovered-work-cells-2026-08-07.md ADR §3.3.1 already ratified shift-scoped material state with inheritance, and explicitly rejected the per-piece capture this set first drew. The rule stays here; the mechanism is delegated (spec §3.6) and pt-heat.html was redrawn to match.

CertProcessor integration — how? Read the Cert Identifier Index. Not the parent list's PO + HeatNumber filter (non-indexed, runs only under a HonorNonIndexedQueriesWarningMayFailRandomly header, and CertProcessor itself calls it “the wrong long-term pattern”); not hpt_server.py's heat_lookup (a LAN-only desk-workstation process, unreachable from Azure, and it searches by Insteel test-report number, not by heat). The index is built (_System/cert_identifier_index.py + backfill + reconciler + smoke + tests), its IdentifierValue column is indexed, and Extrusion Log is already consumer #1 under a ratified contract. WIP reads it — never writes, per the write-ownership standing rule (James, 2026-06-12).
