The conflict to resolve before anyone builds this §3.7 specifies a full Receiver screen. But on 2026-07-22, when the station registry was finalised, James dropped Receiving from it with the reasoning: "it is a function (goods-in / put-away), not a scan station." It was also removed from config.SCAN_STATIONS.
Both can be true — a function with a screen that is not a fabrication scan station, which is exactly what this mockup draws (it scans inbound items against a PO, never a WIP tag at a work centre). But it is worth James confirming that reading rather than assuming it, because the two decisions were made two weeks apart and have not been reconciled in writing.
Nothing here is backed by production data. There is no PO entity, no expected-receipts feed, no vendor record, no receipt or discrepancy entity, and no put-away location model. `Receiving` survives as one of the seven WORKER_ROLES and nothing else.
Adjacent-system question: POs and vendor receipts are ordinarily NetSuite's domain, and the Inventory project already owns a locked NetSuite integration boundary (its ADR-002). If Receiver is built, it should almost certainly read POs across that seam rather than model them here.
