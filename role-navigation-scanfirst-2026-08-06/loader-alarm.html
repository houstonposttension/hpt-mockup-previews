5 / 7 · Loader — wrong-bin alarm, deliberately outside the shared chrome

Everything else in this set is an argument for consolidation. This is the counter-example. The wrong-bin alarm is the loader's primary error-prevention control and it is role-specific by design — the audit lists it as R2, one of nine things that must not be flattened into the shared kit. So it does not render as a toast, a strip, a pill, or a row inside the bar. It takes the whole screen, including the bar, pulses, sounds a tone, vibrates, and blocks every other control until the loader makes a three-way decision.

Frame A is the interrupt. Frame B is the decision that follows it — Switch / Stay / Stop — which is where the bar comes back. Tap either frame to dismiss and see the loader screen underneath.

What this page is arguing Consolidating chrome is not the same as flattening behaviour. The audit named nine role-specific elements (§9.5) that lose capability if normalised — the wrong-bin alarm (R2), the bend-shape thumbnail (R1), the camera viewport's presence or absence (R3), the driver's binary go/no-go (R4), the inventory numeric entry grid (R5), maintenance's external-staleness state (R6), the supervisor's person-axis pivot (R7), the offline queue (R8), and the station picker (R9). This set keeps all nine outside the shared kit. The bar is the thing that unifies; the work is not.
Real today: the alarm, the tone, the vibrate and the three-way Switch / Stay / Stop decision are live in load_app.html. Rev 2 changes none of that behaviour — it only shows what happens to the new bar when the alarm fires (it is covered) and what it looks like when the decision screen takes over (it returns).
Note the third frame element: the context strip renders its empty state while the load is paused, rather than disappearing. The strip's height is reserved so the screen does not jump.
