Bins — compact redesign · supervisor portal · unified active + historical

Problem: today the Bins tab renders every active bin as a two-line card that pre-builds its full drill-down into the DOM, with a ship-date <h3> between every cluster, a 7-column tag table that can't fit 375px, and no search, no filter, no cap. ~20 bins on a busy day scrolls forever. This redesign collapses each bin to one dense row, moves all detail behind a tap-to-open drawer, adds a sticky search + state/stage filter, and folds the (still-unmerged) tag-search feature into the same interface via an Active / Shipped / All state switch.

How a compact row works: the row shows only bin # · top stage badge · weight/tags · ship · % complete. The left edge colour is the bin's least-advanced active lifecycle stage (or blue for MIXED); an attention flag (SHORT / STALE) floats at the corner only when something needs the supervisor. Tap the row to open the drawer: sub-bin → order → the six lifecycle stages → tag rows (tag # · weight · status), each tag itself tap-expandable for shape / scanned-by / when / machine.

The progress bar = shipping-readiness by weight. It fills by the share of the bin's weight that has reached staged-or-beyond (fabricated and ready to load) — not delivered, so it climbs through the day. The label beside it is tags-complete / total, the count a supervisor scans. The two diverge when the heavy tags are the ones still out: X14 is 19 of 21 tags (90%) but only 71% of the shipping weight — the 2 remaining are the big ones. Estimated-time-complete is deliberately absent (no reliable per-tag task-time data). Bar semantics are independent of the left-edge colour: a bin can be well over half ready by weight yet still edged/badged by its least-advanced stage.

⚠ API GAP — costed, not hidden. This mockup draws the target state James approved. Two pieces do not exist in production yet: (1) /api/portal-bins-expanded is active-only — there is no shipped/historical bins query, so the Shipped and All states need new backend work; (2) multi-field search (bin / order # / ticket / tag ID / customer) has no endpoint — the only tag lookup is GA-WIP-108 / PR #54, which is unmerged, flag-gated, and exact-tag-ID-only. The design note breaks this into phases so it's scoped before any build.

6 · Bar treatments STAGED + LOADED

The bar must show two phases: staged (fabricated, ready to load) and loaded (on the truck — a subset of staged). Three treatments, each on the same two bins so the divergence is visible: X14 = 19/21 tags, 71% staged / 43% loaded (big gap); X12 = 17/18 tags, 94% staged / 90% loaded (nearly all on the truck). Loaded = solid green; staged-not-yet-loaded = pale green — reusing the LEAN --ok token.

Design intent (read with the spec). The compaction levers, in order of impact: (1) one-row-per-bin instead of two-line cards — ~2× density before anything opens; (2) drawer disclosure — tag detail is not in the DOM until tapped, unlike today's pre-built .be-exp; (3) the 7-column tag table is retired for a 3-field tag row + tap-deeper; (4) sticky search + Active/Shipped/All state + stage chips replace scrolling; (5) lifecycle-v2 is the taxonomy (six stages), legacy phase names survive only as badge fallback. The unified list is the target James approved — the amber callout above is the honest backend cost: Shipped/All and multi-field search are new endpoints, and tag-history (PR #54) is still unmerged. Frames are static; taps/typing are illustrative, not wired. GA-WIP-219.
